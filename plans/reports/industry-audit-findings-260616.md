### `n1-compliance-report-hascompletedprogram-fanout` — Compliance report fans out hasCompletedProgram per targeted user (unbounded by department size) with nested per-cohort completion eval
- **Dimension:** perf-db · **Confidence:** high
- **Evidence:** server/domains/learning/reports/compliance-use-cases.js:57-58 runs `Promise.all(assignments.map(a => resolveAssignmentStatuses(a)))`. resolveAssignmentStatuses (server/domains/learning/assignment/status-resolver.js:110-124) -> resolveProgramStatuses (status-resolver.js:24-39) loops `for (const user of users)` calling `await hasCompletedProgram(user._id, programId)` per user. Add a repository method that, given userIds + programIds, returns the set of (userId,programId) with an Issued certificate OR a met completion, computed via a few aggregate/$in queries; have resolveProgramStatuses/resolvePathStatuses consume that map instead of per-user awaits. findParticipatingUserIdsForProgram is already batched — extend the same pattern to the completion check.
- **Verify verdict:** confirmed=true, severity→P1. All traces hold on the actual code: buildComplianceReport (compliance-use-cases.js:58) fans out resolveAssignmentStatuses per assignment; resolveProgramStatuses (status-resolver.js:24-27) awaits hasCompletedProgram sequentially per user; findAssignableUsers (repository.js:56-69) resolves whole departments via departmentId:{$in}, so the eslint-disable "bounded" claim is false for department targets (~1000 employees); hasCompletedProgram (prerequisites.js:15-38) issues Certificate.exists + Class.distinct + 2 distincts then loops cohorts calling evaluateCompletion, each ~7 more queries (completion/use-cases.js:27-33) — so uncertified members in a large department drive thousands of sequential round-trips, and the certificate fast-path only short-circuits already-certified learners. The proposed batched fix is real (buildCompletionRollup/buildEvidenceSets at completion-rollup-use-case.js:64-98 already $in-batches the identical signals).

- **Evidence:** client/src/features/users/UsersPage.jsx:300 `const { data: allTeams = [] } = useTeams();` → builds `teamsByUser` map (UsersPage.jsx:301-310). `useTeams` (client/src/hooks/useTeams.js:6-11) calls `teamsAPI.getAll()` with NO pagination/scope params, returning every Team in the org. - **Impact:** At the stated ~1000-employee scale the org may hold hundreds of teams; this pulls them all + their members arrays on every visit to /people to populate one Team/Class column for at most 50 visible rows. Wasted payload + a full-org map rebuild (memoized, so cheap after first build) for data 95% of which is off-page. Not a render storm (single cached query, staleTime 30s default), hence P3.
- **Fix:** Either (a) have the server return the team/class label inline on the paginated user rows, or (b) fetch teams scoped to only the visible page's user ids (e.g. `teamsAPI.getAll({ userIds })`), so the client never holds the entire org's teams to decorate 50 rows.

### `auditlog-action-filter-missing-createdat-compound` — AuditLog ?action= filter has only a single-field index; the mandatory createdAt sort is not covered
- **Dimension:** perf-db · **Confidence:** medium
- **Evidence:** server/routes/auditRoutes.js:33-59 builds a filter that can be `{action}` alone (line 39) and ALWAYS `.sort({createdAt:-1})` (line 53). - **Impact:** With 2-year retention (AuditLog.js:18) a high-cardinality action ('updated','logged-in') can match a very large row set; the uncovered createdAt sort forces an in-memory SORT stage that can exceed the 32MB sort limit and abort, or just run slow. - **Fix:** Add `auditLogSchema.index({ action: 1, createdAt: -1 })` and drop the now-redundant single-field `index: true` on `action`. This serves both the equality filter and the newest-first sort from one index.
