# Wave E3 Session-Instructors — Adversarial Review

Verdict at bottom. Issues prioritized BLOCKER / MAJOR / MINOR. Each: failure scenario, file:line, fix.

## BLOCKER

### B1 — "Open-until-populated" leak proof is FALSE for the read scopes it widens
Design §5d claims widening teacher scope "preserves open-until-populated". It does NOT, because the three read scopes use INCONSISTENT empty-teacherIds semantics today, and the proposed `$or` makes a guest instructor see MORE than just their assigned session under the empty-binding case is not the bug — the real bug is the inverse: the visibility helpers DISAGREE with the policy.
- `helpers/teacher-class-scope.js:3-9` `teacherVisibleClassFilter` includes `{teacherIds:{$exists:false}}` OR `{$size:0}` → empty cohorts ARE visible.
- `domains/schedule/repository.js:67-73` `findTeacherScopedClassIds` includes `{teacherIds:{$size:0}}` → empty visible.
- BUT `domains/learning/session/repository.js:48-51` `findCohortIdsByTeacher` is `Class.find({teacherIds: teacherId})` — does NOT include empty cohorts. And `session/use-cases.js:61-68` `getSession` checks `(session.classId.teacherIds||[]).some(...)` — an EMPTY `teacherIds` array yields `false` → **403**.

So the session list/detail path (`/api/learning/sessions`) already does NOT honor open-until-populated for teachers (a teacher is denied an empty-binding cohort's session), while the attendance/calendar paths DO honor it. The design wires `canAccessSession` (which inherits the policy's permissive `no-binding-set`) into the attendance controller, but for the session read path it proposes a `$or` filter `[{classId:{$in:visibleCohortIds}}, {sessionInstructorIds:me}]` where `visibleCohortIds` comes from `findCohortIdsByTeacher` (the NON-permissive helper). Result: behavior is now THREE-WAY inconsistent (attendance permissive, calendar permissive, session-read restrictive), and `canAccessSession` used in `getSession` would suddenly FLIP `/api/learning/sessions/:id` to permissive on empty cohorts — a silent behavior change/regression risk vs. today's 403, and the integration tests asserting "unrelated teacher → 403" (§8) would now PASS via `no-binding-set` allow for ANY teacher on an empty-binding cohort, masking the leak.
**Fix:** Do not paper over this. Pick ONE semantic and state it: either (a) keep `getSession`/session-list teacher gate restrictive (DON'T route it through `canAccessSession`; instead do `cohortBound OR isSessionInstructor` where cohortBound mirrors the EXISTING restrictive check), or (b) intentionally migrate session-read to permissive and update its tests + the spec MODIFIED delta to call out the behavior change. The plan currently does neither — it claims "no change" while changing it. Add an explicit decision D9 and a test that pins empty-teacherIds behavior per path.

### B2 — `findValidInstructorIds` count check accepts duplicate / mixed ids → bad data passes validation
§4 step 2 + §9 describe `findValidInstructorIds(ids)` as "counts matching `{_id:{$in:ids}, role:{$in:[Teacher,Admin]}, isDeleted:{$ne:true}}`" and rejecting when the count mismatches. A `countDocuments` against `$in` de-dupes by document, so `instructorIds:[A,A]` (len 2) matches count 1 → mismatch → 400 (OK by accident), but `instructorIds:[A,B]` where A is a valid teacher and B==A-as-string-vs-ObjectId, or a list containing one valid + one valid-but-you-also-want-distinctness, can pass/fail unpredictably. Worse: zod `z.array(objectId).max(10)` does not enforce uniqueness, so `[A,A]` is storable and would then be written verbatim (the count guard only blocks if you compare to `ids.length` including dupes). Effective-instructor dedup is only done at calendar time, not at write time → the stored set has dupes, and `effectiveInstructorIds` returns dupes into authz `.includes` (harmless) but pollutes the audit diff and DTO.
**Fix:** Dedupe `instructorIds` in the use-case before validation (`[...new Set(ids.map(String))]`), validate against the DEDUPED length, and store the deduped array. Add `.refine` uniqueness to `setSessionInstructorsBody`. Add a test: `[A,A]` → stored as `[A]` (or 400, pick one).

### B3 — Calendar attendee merge is specified at 4 sites but MISSES the bookCohortSlot path and the post-commit re-fetch shape, breaking fail-soft idempotency
§9 lists calendar re-fetch edits at `scheduleService.js:71-75, 209-212, 298-300, 485-488`. Two problems:
1. The actual calendar attendee source is `createCalendarEventForSchedule` (`scheduleService.js:66-99`) which re-fetches and populates `enrolledUsers` ONLY (line 74). The 4 cited line ranges are the RESPONSE re-fetches (`:209`, `:298`, `:485`) and the calendar helper (`:71`). Adding instructors to the response populate (lines 209/298/485) does nothing for Calendar — Calendar attendees come from line 82 (`attendees: schedule.enrolledUsers`). The design must edit `createCalendarEventForSchedule` (line 71-82) AND `updateScheduleById`-driven `domains/schedule/use-cases.js:173-183` update sync, NOT the response populates. As written, instructors would NEVER appear on calendar invites for the create paths.
2. On UPDATE (`domains/schedule/use-cases.js:171-187`), the calendar patch uses `attendees: populated.enrolledUsers`. If you later add instructors to attendees but a re-save happens (e.g. admin edits time), Google `sendUpdates:'all'` re-emails the instructor each time — there is no idempotency key for "already invited this instructor." Not a regression vs today (learners have the same property), but the design claims "instructors get the invite like learners" without noting the re-notify-on-every-edit behavior. Acceptable but must be stated, and the merge must be applied at the SAME single chokepoint as learners so the two never diverge.
**Fix:** Centralize attendee assembly: add a helper `effectiveAttendeesForSchedule(populatedSchedule, classDoc)` = dedupe-by-email(enrolledUsers ++ effectiveInstructors) and call it from BOTH `createCalendarEventForSchedule` and the update-sync block. Edit `createCalendarEventForSchedule:74` to also `.populate('sessionInstructorIds','name email empCode')` and `.populate('classId','... teacherIds')` so it can resolve effective instructors. Drop the four response-populate edits as the calendar mechanism (keep them only for the API DTO). Add an integration assertion that a created session's Calendar payload (mock the calendar client) includes the instructor email exactly once.

## MAJOR

### M1 — `setSessionInstructors` wrapping a single-doc write in a transaction is YAGNI and fights the codebase
§4 says wrap the single-document `findByIdAndUpdate` in a `withTransaction` "for read-consistency and audit-snapshot parity." There is no multi-doc invariant here (you confirmed: field is orthogonal to booking). A transaction on a single `findById`+`findByIdAndUpdate` adds a replica-set session requirement to a trivial admin write and buys nothing — the `updateScheduleById` is already atomic, and the "validate instructors then write" race (an instructor user gets soft-deleted between validate and write) is benign (stale-but-recoverable; next edit fixes it; authz re-checks role live at access time anyway). KISS violation.
**Fix:** Drop the transaction. Do: load raw schedule (404 if gone) → dedupe+validate instructor ids → `updateScheduleById(id,{sessionInstructorIds},/*no session*/)` → if `null` 404 → audit with before/after. Saves a phase-3 dependency on replica-set sessions for tests.

### M2 — Audit `before` snapshot not captured on the assign path → diff is one-sided
§9 controller line says `auditService.record({action:'instructors-assigned', diff})` but the use-case as described returns only the updated doc. Every other mutation in this repo captures `before` then `diff(before,after)` (`domains/schedule/controller.js:15-24`, backend-conventions.md mandate). The assign path must snapshot the prior `sessionInstructorIds` (and prior effective set) so an auditor can see "removed teacherB, added teacherC." Clearing an override (`[]`) with no `before` is an un-auditable change to who-could-mark-attendance — a compliance gap given attendance is audit-load-bearing.
**Fix:** In the use-case, capture `before = existing.sessionInstructorIds` from the initial raw load; controller records `diff: auditService.diff({sessionInstructorIds: before},{sessionInstructorIds: after})`. Action verb: use existing convention `updated` or a scoped `instructors-assigned` — confirm the audit action enum/whitelist accepts a new verb (grep `auditService` for an allowed-actions list; if none, fine).

### M3 — `attendance-analytics.js:135` and `attendance-scope.js:15` widening to `$or:[{classId:{$in}},{sessionInstructorIds:me}]` changes analytics totals, not just visibility — double-counting risk
The by-team / by-employee analytics roll up Attendance for the teacher's scoped schedule ids. If you widen the scoped `Schedule.distinct` to also include sessions where the teacher is a session-instructor, a teacher who is BOTH cohort-bound to cohort X AND a guest instructor on a session in cohort Y now gets cohort Y's session attendance folded into THEIR by-team/by-employee rollup. That session's learners belong to cohort Y's team, whose own cohort teacher ALSO counts them. This is intended additive visibility, but the analytics aggregation groups by user/team across the union of schedule ids — a learner enrolled in both could be counted once per scoping teacher (fine, separate requests) but within ONE teacher's request the same Attendance row is matched once (distinct schedule ids), so no intra-request double count. The real issue: §8 has NO test asserting analytics NUMBERS are correct under the union (only the calendar grain test). Silent wrong totals in compliance reports are exactly the high-debug-cost failure class.
**Fix:** Add an integration test: teacher bound to X + session-instructor on a Y-session → by-employee analytics for a learner in the Y-session shows that session's records, and a learner NOT in any X/Y-assigned session shows nothing. Pin the exact counts. Also reconsider whether session-instructor scope SHOULD bleed into whole-cohort analytics at all (your Unresolved Q1) — if the answer is "single-session grain only," then analytics-by-team should NOT widen, only per-session attendance read should. The design widens analytics-scope AND calendar AND session-read; that's broader than the stated "single-session grain" guarantee in §5d. Decide and narrow.

### M4 — Route `PUT /:id/instructors` lacks a dedicated rate limiter and the design hand-waves it
§3a says "no new per-route limiter needed (low-frequency admin action)" relying on the global cap. Every other state-changing admin write here either rides `roleGuard('Admin')` + global limiter (acceptable) — so this is consistent. BUT the design routes auth through `requireCapability('session.assign-instructor')` ONLY, dropping the `roleGuard('Admin')` belt-and-suspenders that the sibling `PUT /:id` uses (`scheduleRoutes.js:40`). Since the new capability `SESSION_ASSIGN_INSTRUCTOR` would be added to `ALL_CAPABILITIES` (Admin-only by §9), capability alone is sufficient — but ANY future edit to the role map that grants a Teacher this cap silently opens the route with no second gate. Minor defense-in-depth gap, not a hole today.
**Fix (cheap):** Add `roleGuard('Admin')` alongside `requireCapability` on the route, OR explicitly document in capabilities.js that this cap is intentionally Admin-exclusive and add a unit test asserting `roleHasCapability('Teacher','session.assign-instructor')===false` and `('Participant',...)===false`. The §8 deny test covers Participant; add the Teacher case.

## MINOR

### m1 — Index `{sessionInstructorIds:1, startTime:1}` is multikey-on-array; verify it's actually used
The reverse lookup `{sessionInstructorIds: actor._id}` (equality on array) uses the multikey index prefix fine. But `findSessionScopeForTeacher` returns an `$or` combining `{classId:{$in}}` and `{sessionInstructorIds:me}`; Mongo cannot use one index for both `$or` branches efficiently and will index-merge or collection-scan one branch. On ~1000 employees / modest schedule counts this is fine (KISS-acceptable), but don't claim the new index makes the `$or` cheap — it only helps the instructor branch.
**Fix:** Note the `$or` uses index-union; acceptable at this scale. No action beyond honest comment.

### m2 — DTO emits `effectiveInstructors` but `sessionDto` has no access to the cohort's teacherIds in all call sites
`sessionDto` (`session/dto.js:27-59`) computes from the populated `schedule`. `effectiveInstructors = sessionInstructorIds ?? classId.teacherIds` requires `classId.teacherIds` to be populated. `populateSessionQuery` (`session/repository.js:13`) already selects `teacherIds` — good. BUT the legacy schedule reads (`domains/schedule/repository.js:9-13` `findScheduleById`, `:32-39` `findSchedulesPage`) populate `classId` with only `'classCode courseName'` (+ `totalSessions`). The design's §3c says add the populate there, but if a reviewer wires the DTO before adding `teacherIds` to those selects, `effectiveInstructors` silently returns `[]` for inherited sessions on the `/api/schedules` surface → UI shows "no instructors" for every legacy session.
**Fix:** Ensure `findScheduleById`/`findSchedulesPage` add `teacherIds` to the `classId` select AND populate `sessionInstructorIds`. Add a DTO unit test: inherited session (empty override, non-empty cohort teacherIds) → `effectiveInstructors == cohort.teacherIds`.

### m3 — "Schedule is hard-deleted on cancel by design" used to justify no soft-delete — but instructor assignment touches attendance-authz, an audit-sensitive surface
The field itself is fine to hard-delete with the schedule (it's session metadata). But CLEARING an override (admin sets `[]`) removes a teacher's attendance-mark access with the only record being the audit diff (see M2). That's the soft-delete spirit (recoverable trail) satisfied by audit, not by a tombstone — acceptable, provided M2 (before-snapshot) is fixed. Flagging so the "no soft-delete needed" line isn't read as "no durable trail needed."
**Fix:** None beyond M2.

### m4 — Started-session / past-session guard not addressed for instructor assignment
`deleteSchedule` blocks deleting started sessions (`use-cases.js:208`). The assign endpoint has no such guard — an admin can reassign instructors on a session that already happened. Probably desired (correcting who-taught for records), but undefined. Also: assigning an instructor to a past session does NOT re-send a calendar invite usefully (event is in the past) yet `sendUpdates:'all'` will still email. 
**Fix:** Decide explicitly: allow assign on past sessions (yes, for record correction) but SKIP calendar sync when `startTime <= now` to avoid spurious past-event emails. One-line guard in the use-case's calendar-sync branch.

### m5 — `max(10)` instructors per session is unjustified breadth (YAGNI)
Your Unresolved Q2. For 1-hour internal sessions, 10 co-instructors is implausible; 3 matches the "≤~3-element list" assumption you used to reject a join collection in D6. Larger cap = larger audit diffs + more calendar attendees.
**Fix:** Set `.max(3)` (or 5) unless ops gives a concrete reason. Cheaper to widen later than to narrow after data exists.

## Things the design got RIGHT (don't re-litigate)
- Override-or-inherit (D1) + UNION authz (D2) is the correct shape; cohort teacher never losing access is properly argued and matches `isTeacherOfClass` returning the cohort decision first.
- No new unique constraint; field is genuinely orthogonal to the `{classId,startTime}` double-booking invariant (verified: `assertBookable` never touches it). B1/E2 ordering untouched — correct.
- Reusing `classBinding.isTeacherOfClass` instead of forking it (DRY) — good.
- Additive nullable field, `[]` default, zero backfill, clean rollback — compat story is sound for OLD DATA (the gap is in the READ-SCOPE consistency, B1, not the data model).
- No learner field feeds learner gating — verified `getScheduleById:102-110` and `getSession:53-60` are enrollment-only and untouched. The "no learner write/leak" claim holds AS LONG AS the scope filters only ever read `teacherIds`/`sessionInstructorIds` (they do).

## Unresolved questions (for the human)
1. Single-session grain vs cohort-analytics bleed (M3): should a guest session-instructor's assigned session appear in by-team/by-employee analytics, or ONLY in per-session attendance + calendar? The design silently chose "yes, bleeds into analytics" — confirm or narrow.
2. Empty-teacherIds semantics on the session-read path (B1): migrate `/api/learning/sessions` to permissive (matching attendance), or keep it restrictive and route instructor-union WITHOUT `canAccessSession`? This is a real behavior decision, not a wiring detail.
3. Instructor cap 3 vs 10 (m5).
